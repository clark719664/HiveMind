# A real BOINC server (built from source) for the HiveMind QLoRA MoE apps

The emulator of `docs/BOINC_REAL_CLIENT.md` was a stand-in. This page documents the same apps running against **BOINC's own
server software** (7.24.4, built from source), with real code-signed app versions, BOINC's own scheduler, upload handler,
`script_validator` and `script_assimilator`, driven by a stock 7.18.1 client on the Tesla T4. Criteria were written before
the first run: `artifacts/boinc_prod_server/ACCEPTANCE.md`.

**It is a production-grade stack on one machine, not a public production deployment**: loopback only, one volunteer host,
the code-signing private key on the same server (BOINC itself warns this is a vulnerability for a public project).

## Layout (all unprivileged, nothing installed as a service)

| Piece | How it runs |
| --- | --- |
| MariaDB 10.6 | private instance, data on the big disk, `--skip-networking` (socket `/run/mysqld/mysqld.sock`; **no TCP listener at all**) |
| Apache 2.4 + mod_php | private instance (`apache.conf` generated by `server_stack.py`), `127.0.0.1:8081`; the VM's own nginx on 80/443 is untouched |
| BOINC daemons | `feeder`, `transitioner`, `file_deleter`, and for each app a `script_validator` and `script_assimilator` |
| Apps | `hivemind_qlora_moe`, `hivemind_moe_infer`, version 100, platform `x86_64-pc-linux-gnu`, plan class `cuda_hivemind` (NVIDIA, ≥ 3,500 MB), signed with the project key |
| Hooks | `boinc_server_scripts.py` (validate / assimilate) → `MoEValidator` (random-segment replay) and the adapter store |

## Runbook

```bash
# once: system packages (do NOT leave their services enabled), a build of the server, a venv with peft + bitsandbytes
sudo apt-get install --no-install-recommends mariadb-server libmariadb-dev libmariadb-dev-compat apache2 libapache2-mod-php php php-mysql \
     php-gd php-xml php-curl python3-mysqldb autoconf automake libtool xsltproc   # then: sudo systemctl disable --now apache2 mariadb
cd BOINC_SRC && ./_autosetup && ./configure --disable-client --disable-manager --disable-fcgi --enable-server --enable-libraries && make -k -j2
sudo install -d -o $USER /run/mysqld            # once per boot (tmpfs)
mariadb-install-db --no-defaults --datadir=BASE/mysql/data --auth-root-authentication-method=normal --skip-test-db
python3 scripts/boinc_server_stack.py setup --base BASE --boinc-src BOINC_SRC --venv-python VENV/bin/python   # make_project, apps, daemons config
(cd BASE/project/hmproj && yes y | bin/update_versions)                                                          # signed app versions
python3 scripts/boinc_server_stack.py start --base BASE --boinc-src BOINC_SRC --venv-python VENV/bin/python
python3 scripts/boinc_prod_server_e2e.py ...                                                                     # the end-to-end test
python3 scripts/boinc_server_stack.py stop  ...
```

### How C3 was scored (not hidden)

The script scored C3 false: it looked for the emulator's file names (`hmp_good_001_0_0`), but the real server names outputs
`hmp_good_001_0_r546187683_0`. The upload itself had succeeded (the validator read both files). I fixed the matcher and
rescored **on the stored full client log** (`scripts/boinc_prod_server_rescore.py`; the original criteria are kept as
`criteria_original` in the report). That is a rescoring, not a new run. A separate crash at the very end of the first
script version (`del torch`) happened after the report was written and affected nothing.

## What was different from the emulator (findings, in the order they bit)

1. `./configure --disable-static` breaks the unneeded `zip` helper (`libboinc_zip.a` is required); `make -k` builds every server binary used here. Parallel `make -j4` also hit a libtool `.deps` race; `-j2` resumed fine.
2. The project scripts use `#!/usr/bin/env python`; this VM has only `python3`. A private `python` symlink on `PATH` is used instead of a system package.
3. `make_project` writes `<host>127</host>` (from the URL) into `config.xml`; `bin/start` matches it against the machine's hostname and otherwise says "No daemons for this host".
4. Two daemons with the same executable (`script_validator` for two apps) need distinct `<output>` and `<pid_file>`, or only the first starts.
5. Ubuntu's Apache has `log_config` and `unixd` built in; loading them as modules is an error.
6. `html/user/schedulers.txt` ships with a commented `<scheduler>` and a placeholder `href="url"`: the client tried the placeholder first ("Couldn't resolve host name") before falling back. Fixed by `Stack.fix_scheduler_list`.
7. `create_work` stages inputs itself (copies `download/<name>` into the hashed directory); an extra `stage_file` step moved them away.
8. A rejected result is **retried by BOINC** (`max_total_results`): the lazy workunit was run three times on the T4 before the run ended, and the last copy was left "in progress" on the (now closed) client. Production should set `max_total_results` low for deterministic apps.

## Two things to decide before anyone relies on the credit numbers

* **BOINC's native credit and HiveMind's `verified_credit` disagree by an order of magnitude.** The same workunit earned 267.7 from BOINC (it trusts the client's claimed work, capped at the project maximum) and 56.9 cobblestones from `verified_credit` (which caps by the card's measured peak); the inference workunit 55.2 vs 0.09. The ledger (`hivemind_ledger/verdict_*.json`) records the HiveMind value next to BOINC's. Making BOINC grant the HiveMind value (a custom validator or `--credit` handling) is not done.
* **The validator loads the model for every result** (~10–25 s) and shares the GPU with the volunteer's task. Fine for one host; a pool would keep a resident validator.

### Resident validator (optional)

Off by default; nothing changes on a node until its owner turns it on. `src/hivemind/boinc/real_client/resident_validator.py` adds a small
local service that keeps the validator's base model loaded between results, so the ~10-25 s load above (that figure is this document's own,
not re-measured by the change) is paid once per model instead of once per result.

* **Server.** `python3 -m hivemind.boinc.real_client.resident_validator serve --socket /run/hivemind/rv/rv.sock --work-root <upload dir>`
  (optional `--max-entries`, `--max-bytes`, `--timeout`, `--preload MODEL_ID [--rank --alpha --init-seed]`). It loads nothing until the first
  request. The socket is a UNIX domain socket only (no TCP listener, nothing on a network interface), its directory must be owned by the
  user with mode 0700, the socket is mode 0600. The server must run with the same environment as the validator shim
  (`HIVEMIND_SPEC_DIR`, `HIVEMIND_LEDGER_DIR`, and for community mode `HIVEMIND_STACK_BASE`/`HIVEMIND_BOINC_SRC`). SIGTERM unloads the models
  and removes the socket. `ping` and `stats` (cache hits, misses, loads, evictions, estimated seconds saved) go through the same CLI.
* **Client.** `hivemind_validate` forwards to the server when `HIVEMIND_RESIDENT_VALIDATOR_SOCKET` is set (or with `--resident[=SOCKET]` as the
  first argument). If the socket is missing, refuses or fails, it prints one warning line and runs today's one-shot validation, so a
  validation never fails because the resident server is down. With the variable unset the code path is the old one (a test proves the
  resident module is not even imported).
* **Same verdicts.** Both paths call `boinc_server_scripts.run_validation`; only the source of the base model differs (a cache keyed by model id,
  quantisation + LoRA-init signature and device). `tests/test_resident_validator.py` runs three results both ways with a fake model and requires
  identical exit codes, log lines and ledger verdicts, and one model load instead of three.
* **Limits of the service.** Paths outside `--work-root` are refused, messages are capped at 1 MiB, each request has a timeout (a validation
  that outlives it keeps running in the server, the client falls back to one-shot). Validations are serialised. Inference workunits
  (`hivemind_moe_infer`) still load their own model copy in `infer`, as before.
* **Not solved here: GPU memory sharing.** A resident model stays in VRAM while a volunteer's task runs on the same card; this layer only removes
  the repeated load and does nothing about contention or about fitting both in memory. The owner decides whether and when to enable it on the live
  node (and whether to give it a `--max-bytes` budget); it has not been run against a real model or GPU.

## Limits

One host, one GPU, one seed, five results. Base model, toy-scale training. The server keeps its signing key online. No TLS, no
public hostname, no systemd units (the stack runs under the session that started it and does not survive a reboot:
`/run/mysqld` is recreated per boot, then `boinc_server_stack.py start`). `deploy/t4_node/README.md` covers what making the T4
reachable by new users involves and why that is the owner's step.
