# S-3 result: can a language model turn a plain-language science question into a solvable specification? (first run, 2026-10-27)

Pre-registration: `artifacts/experiments/S3_formulation_prereg.json` (questions frozen before any model run, sha256 in `S3_questions.sha256`) and amendment 1 (`S3_formulation_prereg_amendment_1.json`). Arm files: `S3_formulation_model_qwen2.5-coder-7b-instruct_gpu.json` and `S3_formulation_baseline_baseline_cpu_10families.json`. Report script: `scripts/s3_paired_report.py`.

## What was run
- **Model arm:** `qwen2.5-coder:7b-instruct` (the model the live node already serves), temperature 0, through the node's own Ollama, **one request at a time, once**, in the owner's night window (about 22:35 to 22:45 Paris). 40 questions (24 English, 16 French), three tiers: **A** direct (family and numbers in SI units), **B** paraphrased, **C** implicit (a unit conversion or a derived parameter is needed). Up to 3 retries per question with the exact validation error fed back. The solver is the pinned `hivemind-solver` (10 families) in the namespace sandbox; the verifier is the stage-2 verifier with tolerance policy v1.
- **Baseline arm:** a keyword and template formulator, no model, deterministic, same solver binary.
- **Total model-arm time:** 493 s; median 6.3 s per question; the first question took 133.5 s because the model was not resident and had to be loaded (a single observation of a cold start on this node).

## Deviations you must know about
1. **The CPU model arm was not obtained.** A 1.5B model on a private CPU-only server timed out on every call (300 s) because other jobs on the shared machine used all eight cores (load about 11). Those records are infrastructure failures, not results, and were discarded. Rule A1 (defined for the CPU arm) is therefore **not evaluable**, and the registered analysis script `s3_analyze.py`, which requires a CPU arm file, could not be used. `s3_paired_report.py` computes the same paired tests without it.
2. **The baseline was re-run (amendment 1).** The first baseline file used a 6-family solver binary, which made it UNVERIFIED on every pendulum, projectile, Kepler and logistic question for a reason unrelated to its formulation. It was re-run with the same 10-family binary as the model arm, deterministically. Both files are kept. The comparison below uses the re-run.
3. One run, temperature 0: there is no estimate of run-to-run variation.

## Results (model 7B on the node's GPU versus the keyword baseline; paired exact test)

| Metric | Tier A (n=13) | Tier B (n=15) | Tier C (n=12) | All (n=40) |
|---|---|---|---|---|
| **Registered primary**: VERIFIED or AUDITED **and** numbers agree. Model / baseline | 6 / 8 (p = 0.50) | **8 / 1 (p = 0.016)** | 1 / 0 (p = 1.0) | 15 / 9 (**p = 0.109**) |
| Secondary: final spec equals the expected spec. Model / baseline | 10 / 12 (p = 0.50) | **10 / 1 (p = 0.004)** | 2 / 0 (p = 0.50) | **22 / 13 (p = 0.023)** |
| Secondary: numbers agree, any verdict. Model / baseline | 10 / 12 (p = 0.50) | **10 / 1 (p = 0.004)** | 2 / 0 (p = 0.50) | **22 / 13 (p = 0.023)** |

Registered rules: **A1** not evaluable (no CPU arm). **A2** reported per tier, above. **A3** (zero answers presented as VERIFIED whose numbers are wrong): **PASS, 0** (see the warning below). **A4** (the limits sentence in every response): **PASS, 40 of 40**.

## What the numbers say, and what they do not
- **The model clearly beats the baseline on paraphrased questions** (tier B: 8 correct versus 1; the baseline's keyword patterns break when the wording changes).
- **On direct questions (tier A) the model did not beat the baseline** (6 versus 8 on the primary metric; 10 versus 12 on exact spec). The 7B model is not an improvement where a small keyword matcher already works.
- **Tier C is essentially unsolved by both** (model 1 correct, 2 exact specs). Questions that need a unit conversion or a derived parameter (minutes to seconds, length and period to g/l) are where the model chose the wrong numbers.
- **The overall primary-metric difference is not significant** (15 versus 9, p = 0.109, 40 questions, one run). The significant results are in tier B and in the secondary spec-match metric; the latter is a more direct measure of formulation, but it was a secondary metric.
- **The registered primary metric undercounts the model.** Seven answers whose numbers were right (`q01 q02 q05 q11 q17 q18 q32`: pendulum, Kepler and a spring-mass case) got the verdict FAILED because the tolerance policy v1 rejects them, as documented in `docs/solver_bee/SOLVER_HELDOUT.md`. The primary metric therefore partly measures the solver's accuracy policy, not the model.

## Where the model failed
- **Could not formulate (12 of 40):** `sir` 4 of 4, `rlc` 4 of 4, `msd` (spring-mass) 2 of 4, `stiff` 1 of 3, `pendulum` 1 of 4. After 3 retries the proposal still did not pass validation. These are the models that must be expressed through the generic `mass_action` or `linear` kinds. The model handled the named families (Kepler, logistic, projectile, chains) without any failure to formulate.
- **A warning about the wording AUDITED.** **4 of the 19 AUDITED answers were numerically wrong** (`q30 q33 q35 q39`, all tier C): the model solved a different problem than the one asked, and the solver and verifier cannot know. A3 only counts VERIFIED, so it passed, but a reader may take AUDITED as reassurance. AUDITED means the stated equations were solved consistently, nothing more. The answer's plain-language summary shows the interpreted problem so the user can catch it, but this is the clearest risk found so far.

## Consequences (proposals, not done)
1. **Do not let the model write raw specs for epidemics and circuits.** Have it fill a few named slots (family, parameters, initial values, times) and let deterministic code build the `mass_action` or `linear` spec from `families.py`. Pre-register this as S-3b, with the same questions.
2. **Echo back before solving:** show the interpreted problem in plain words and ask the user to confirm it, and reword AUDITED to say that the equations were solved but not checked against the question.
3. **Certify the accuracy actually achieved**, or tighten automatically, so that correct pendulum and Kepler answers are not marked FAILED (see the held-out result in `SOLVER_HELDOUT.md`).
4. **Unit conversions:** require the question's units to be explicit, or add a deterministic unit step; do not ask the model to convert silently.
